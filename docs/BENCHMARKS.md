# Benchmarks

script in this repository, so you can re-run it on your own hardware. Treat
these figures as a lower bound on what is validated. Anything not listed
here has not been measured.

## 2. Capture accuracy (ground truth)

Every request is generated by an oracle that logs what it sent and what came
back (`truth.jsonl`). Each request carries a unique token, and a scorer matches
the agent's JSONL export against the truth file. The scorer reports the
following:

- **recall**: share of real exchanges the agent exported;
- **duplicates / phantoms**: exports that match no exchange, or match one twice;
- **field accuracy**: method, status, response size, path;
- **PII visibility**: share of requests that carried PII (emails, SSNs and
  cards in bodies, query parameters and SQL literals) that the agent flagged;
- **leaks**: raw PII values found anywhere in the export. This must be zero.

### HTTP/1.1

`tests/oracle/run.sh`: keep-alive connections of up to 6 requests; GET, POST
with a JSON body containing an email and an SSN, chunked responses, and
bodies from 0 B to 12 KB (more than one 4 KB capture slot).

| Run | Exchanges | Recall | Dups / phantoms | Status / method | Response size | POST bodies captured / redacted | Leaks |
|---|---|---|---|---|---|---|---|
| Before this release (seed 1234) | 2,000 | 8.2% | — | — | — | — | — |
| Current, seeds 1234, 7, 99, 42, 77 | 2,000 each | 100% | 0 / 0 | 100% | 99.8–99.9% | 100% / 100% | 0 |
| Current, load run, seed 42 | 5,000 | 100% | 0 / 0 | 100% | 99.9% | 1,008 / 1,008 | 0 |

Recall is 100% at every keep-alive position (1st through 6th request). The
response-size misses are all large chunked responses where some packets were
lost from capture. The exchange is still exported and the size is
under-reported.

### HTTPS, Go `crypto/tls`

`tests/oracle/run_tls.sh` (go stack): a Go `net/http` client and server
(`go_tls_oracle.go`, HTTP/1.1 over TLS, keep-alive, GETs up to 70 KB and POSTs
with an email and an SSN). Writes are hooked at `(*Conn).Write`. Reads use
an entry probe plus a uprobe on every `RET` instruction of `(*Conn).Read`,
keyed by goroutine, because uretprobes break when Go moves goroutine stacks.

| Run | Exchanges | Recall (client / server view) | Status / method / size | With socket addresses | Leaks |
|---|---|---|---|---|---|
| Before (writes only, PID-scoped probes) | 300 | 0% / 0% | — | — | — |
| Current, seed 42 | 500 | **100% / 100%** | 100% / 100% / 100% | 100% / 99.6% | 0 |
| HTTP/2 (`go-h2` stack), before | 300 | 55–65% / 55–65% | — | — | 0 |
| HTTP/2 (`go-h2` stack), current, seeds 7, 14, 42 | 300–500 | **100% / 100%** | 100% / 100% / 100% | 100% / 100% | 0 |

HTTP/2 over TLS had two problems of its own:

- **Connection keys were reused.** Go and OpenSSL reuse the memory of a closed
  connection object, so a new connection can get the same `*tls.Conn` /
  `SSL*` key. Its preface then landed in the old connection's parser, along
  with its stale HPACK state. A client preface now restarts the parser.
- **Large reads and writes were cut.** One TLS read or write often holds a
  whole 16 KB record, which is several frames, while each event carries at
  most 4 KB. The probes now emit a call as up to four consecutive 4 KB events,
  so parsers see the stream contiguously.

Before this fix, the client process was not hooked at all. The probes were
PID-scoped, and a second process running an already-hooked binary was
skipped. Every replica of a Go service on a node was affected. Probes now
cover every process that runs the binary, as they do for `libssl`. POST
bodies are cut at `max_body_bytes` (4 KB). Go's JSON encoder sorts keys, so
in the 5 KB POSTs the SSN falls past the cut. It is then neither exported
nor redacted, which is why only 75 of 117 bodies show redaction.

### HTTPS (OpenSSL uprobes)

`tests/oracle/run_tls.sh`: the same HTTP/1.1 mix over TLS on loopback,
generated by CPython, which uses the system OpenSSL 3.0 (`SSL_read_ex` /
`SSL_write_ex`). The uprobes see both ends, so each exchange is exported once
from the client process and once from the server process, and each view is
scored on its own.

| Run | Exchanges | Recall (client view / server view) | Dups | Status / method / size | With socket addresses | POST bodies redacted | Leaks |
|---|---|---|---|---|---|---|---|
| Before this release | 300 | 0% / 0% | — | — | 0% | — | — |
| Current, seed 42 | 1,000 | **100% / 100%** | 0 | 100% / 100% / 100% | **100% / 100%** | 197 / 197 per view | 0 |

There were two causes of the 0%:

- Only `SSL_read`/`SSL_write` were hooked, while OpenSSL 1.1.1+ applications
  (CPython, curl, recent nginx) call the `_ex` variants.
- TLS connections were keyed per thread, with the direction relative to the
  process. So server processes had requests parsed as responses, and
  connections interleaved on one event-loop thread were mixed together.

Connections are now keyed on the library's `SSL*`, and the client/server role
is inferred from the first payload. Socket addresses come from the
`sock:sock_send_length` / `sock_recv_length` tracepoints firing inside a
hooked TLS call (fentry or kprobes on older kernels, not validated here: this
VM has kprobes compiled out and kernel lockdown blocks fentry).

Response sizes are exact even for 70 KB bodies, because each `SSL_read` /
`SSL_write` buffer beyond 4 KB is accounted for as a gap, which the parser
skips.

for each.

| Protocol | Traffic mix | Recall before → now | PII visibility before → now | Leaks |
|---|---|---|---|---|
| Redis 7.4 | SET/GET/HSET/LPUSH/INCRBY/DEL, errors, pipelined batches | 86.2% (GET 0%) → **100%** | 0% → **100%** | 0 |
| PostgreSQL 16 | simple queries, extended protocol (Parse/Bind/Execute), named prepared statements, errors | 45.6% → **100%** | 0% → **100%** | 0 |
| MySQL 8.4 | COM_QUERY text protocol, errors, `caching_sha2_password` auth | 0% (see below) → **100%** | 0% → **100%** | 0 |
| MySQL 8.4, prepared statements | mysql-connector-python prepared cursors (COM_STMT_PREPARE / EXECUTE / CLOSE, statements re-executed with new values), mixed with text queries | 66.7% → **100%** (re-executed statements 0% → 100%; verb accuracy 49.5% → 100%) | 0% → **100%** | 0 |
| gRPC (HTTP/2) | unary, server-streaming, trailers-only errors (`NOT_FOUND`) | 100% → **100%** | 65% → **100%** | 0 |

gRPC field accuracy went from 21% to 100% for the method path and from 79% to
100% for `grpc-status`. Before the fix, the HTTP status of 200 was reported
even for failed calls.

The latest full runs (seeds 7 and 42) have every protocol at 100%; Redis was
also checked with seeds 21 and 99.

### Kafka, AMQP (RabbitMQ), DNS

`tests/oracle/run_messaging.sh`: a fresh agent per protocol. Every operation
puts its token in the record key/value, routing key, message body or query
name; bodies carry an email. Besides the operations themselves, the truth
includes every record a consumer received back, so 500 operations give
about 740 Kafka and 910 AMQP truth entries.

| Protocol | Traffic mix | Recall before → now | Field accuracy now | PII visibility before → now | Leaks |
|---|---|---|---|---|---|
| Kafka 3.8 | librdkafka Produce v10 (single records with and without headers, multi-record batches, `MESSAGE_TOO_LARGE` rejections), kafka-python Produce v8, concurrent consumer (Fetch v16, topic IDs), Metadata v1/v4/v9/v12 for missing topics | 0% → **100%** | topic, API, error code 100% | 0% → **100%** | 0 |
| RabbitMQ 3.13 | Basic.Publish to topic, fanout, direct and default exchanges, publisher confirms, 6 KB bodies, unroutable mandatory publishes (Basic.Return 312), Basic.Get (also on missing queues: 404), Basic.Consume deliveries, Basic.Ack | 43.7% (Get, Return 0%) → **100%** | method, exchange/routing key or queue, reply code 100%; client acks 372/372 | 0% → **100%** | 0 |
| DNS | A, AAAA, CNAME chains, NXDOMAIN, SERVFAIL, TXT; 10% over TCP | 90.2% (TCP 0%) → **100%** | query name, type, rcode, answers 100% | — | 0 |

Measured with seed 7 (500 operations) and seed 42 (1,000 operations, also
100% everywhere, 0 duplicates). What was wrong before:

- **Kafka**: the topic was read at a fixed offset, wrong for every version
  current clients send (Produce v3+ starts with `transactional_id`; v9+,
  Fetch v12+ and Metadata v9+ use compact encodings and tagged fields;
  Fetch v13+ names topics by ID), so no exchange had a topic. Records were
  never decoded, so produced and fetched values (and the PII in them) were
  invisible. The error code was read at a fixed offset (Produce responses
  reported values like 29284). Requests and responses were exported
  separately. A Fetch response larger than the 256 KB buffer closed the
  connection's parser, and a capture gap reset it.
- **AMQP**: message bodies were never read, Basic.Get and GetOk were
  unrelated records with no queue or body, a Basic.Get on a missing queue
  showed no error, Basic.Return had no reply code, and every method frame
  (Channel.Open/OpenOk/CloseOk...) was a record of its own. A capture gap in
  a large message desynchronised the stream.
- **DNS**: queries and responses were exported as two records, the rcode
  only on the second; DNS over TCP (length-prefixed) was not parsed; AAAA
  answers were not in canonical form (`fd00:0:0:0:0:0:0:2a`).

Exchanges are now one record each, exported at the response (Kafka, DNS,
AMQP synchronous methods), or when the message content is complete (AMQP
publish, deliver, return). IPv4 answers in DNS records are redacted to
`<IP_V4>` by the default PII policy.

## 3. Overhead

### Kernel (per captured packet)

The kernel runtime of the TC classifier is measured with
`kernel.bpf_stats_enabled=1`, reading `run_time_ns / run_cnt` from the
program's fdinfo (`tests/oracle/bpf_cost.py`). This is the time the kernel
spends in Panopticon's eBPF program for each packet on the monitored
interface. It is not end-to-end latency.

| Path | ns / packet |
|---|---|
| Before this release | 12,500–15,000 |
| Current, TCP packet with payload (captured) | 1,200–2,000 |
| Current, packet that is not captured (e.g. ICMP) | ~85 |
| Under sustained load (~40K packets/s), before the wakeup fix | 6,643 |
| Under sustained load (~40K packets/s), current | 1,600–1,700 |

With TLS capture on (`tls_scan_enabled`, the default), two more hooks run on
**every TCP send and receive on the node**, not only TLS ones, to learn TLS
connections' addresses. They cost 80–300 ns per call on this VM (about 80 ns
under sustained load), against ~100 ns for an empty program on the same
hooks. Turn TLS capture off to remove them.

Two changes account for most of the gain. The payload is now copied with one
`bpf_skb_load_bytes` instead of byte by byte. Ring-buffer wakeups are now
batched, where previously every event woke user space, which was about 90% of
the cost.

### Agent (user space)

These figures come from `tests/oracle/run.sh 5000 42`. The generator is a
single Python client, so it produces about 39 exchanges/s (21K events). That
measures cost per event and memory under sustained traffic; **it is not a
throughput ceiling**.

| | Before | Current |
|---|---|---|
| Agent CPU over the run (128 s) | 7.61 s (5.9% of one core) | **2.98 s (2.3%)** |
| Peak RSS | 367 MiB | **122 MiB** |
| Idle CPU (no traffic) | 4.4% of one core | **1.0%** |
| Idle steady-state RSS | 88 MiB | 56–90 MiB |

Most of the old peak came from the TLS library scanner reading every
executable on the host whole into memory, and most of the old idle CPU came
from a fixed 2 ms ring-buffer drain tick. Both are fixed: the scanner reads
only ELF headers and symbol tables, and the tick backs off to 16 ms while
idle and returns to 2 ms as soon as events arrive.

### Sustained load and connection churn

`tests/load/run_load.sh` drives HTTP/1.1 through the same veth topology with
a Go load generator (`tests/load/loadgen.go`), and reports the achieved
rate, capture recall, drops by cause, agent CPU and peak RSS. The VM has 4
vCPUs shared by the load generator, its server and the agent, so the rates
below are limited by the generator, not by the agent.

64 keep-alive connections, as fast as possible, 512 B responses, 20% POSTs
with an email in the body (`run_load.sh 64 20s`):

| | Before | Current |
|---|---|---|
| Achieved load | 17.7K req/s | 21.7–23.1K req/s |
| Capture recall | 97.35% | 99.99–100% |
| Events dropped | 2.5% (worker queues full) | 0–0.01% |
| Kernel TC cost per packet | 7,453 ns | 1,599–1,693 ns |
| Agent CPU | 78% of one core | 58–60% |
| Peak RSS | 224 MiB | 97–101 MiB |

Large responses, 200 KB bodies over 200 connections
(`run_load.sh 200 20s 0 0 200000`, about 1.8 GB/s through the veth):

| | Before | Current |
|---|---|---|
| Achieved load | 7.5K req/s | 9.1K req/s |
| Capture recall | 43.9% | 98.0–98.3% |
| Drops (kernel / workers / export) | 90K / 34K / 63K | 0–16K / 0.5–16K / 0 |
| Agent CPU | 116% of one core | 60–64% |
| Peak RSS | 233 MiB | 114–137 MiB |

Before, every exchange carried up to 64 KB of body text through PII
scanning, the export queue and the JSON writer. Bodies are now cut to
`max_body_bytes` (default 4 KB) before any of those stages, so the
redaction still covers everything that is exported. The remaining drops
come in bursts, while the load generator saturates the VM's 4 vCPUs.
Running the ring buffer drain on its own thread (also tried at raised
priority) did not reduce them measurably here, so that change was not kept.

Connection churn, one request per TCP connection (`run_load.sh 64 30s 0 1`):
8.4K connections/s with 99.98% recall. Tracked connections stay at 0–36,
because the parser state of a connection is dropped on its FIN/RST. Before
that, about 14K stale entries waited for the 30 s idle timeout, and heavier
churn would have hit the 65,536-entry table limit and evicted live
connections. The service graph stays at one edge, where it used to gain a
node and an edge per client connection.

### Where the CPU goes

`--replay-bench FILE` runs a raw capture (`--capture-raw`) through the same
worker code as live traffic, on one core, without the kernel or scheduling
noise. Here it is the 64-connection load above (43K events):

| Pipeline | Before | Current | Events/s on one core |
|---|---|---|---|
| Parse only (PII and graph off) | 3.46 µs/event | 1.5–1.7 µs | ~600K |
| Parse + PII + graph | 6.25 µs | 4.5–4.8 µs | ~210K |
| Parse + PII + graph + JSON export | 14.64 µs | 6.5–7.6 µs | ~150K |

The biggest gains came from three changes:

- **Allocator.** glibc's malloc arena locks were about 20% of busy samples,
  because workers allocate messages that the export thread frees. The agent
  now uses mimalloc.
- **JSON export.** It used to flush and `write(2)` after every exchange.
- **Graph templates.** Every request with a unique query string became its own
  graph template, which cost memory as well as CPU.

Live, the agent spends about 15 µs of CPU per event at this load. The
difference from the replay figure is the kernel-to-user hand-off and
contention for the VM's 4 vCPUs. Plan on roughly one core per 60K
captured packets per second with JSON export on.

Not measured yet: throughput above ~25K requests/s (the load generator is the
limit on this VM), kernel-to-export latency percentiles, and memory with the
ONNX model loaded.

## 4. Micro-benchmarks

Criterion, `cargo bench -p panopticon-agent`. The benchmarks call the real
parsers and PII engine, and each one asserts it produced the expected result
before it is timed. Values are medians.

| Benchmark | Median |
|---|---|
| HTTP/1.1 request + response, 156 B body | 1.42 µs |
| HTTP/1.1 request + response, 16 KB body | 3.41 µs (~4.5 GiB/s) |
| Redis `SET` + reply | 147 ns |
| PostgreSQL simple query + result | 412 ns |
| MySQL `COM_QUERY` + OK | 301 ns |
| Protocol detection, per payload | 2–10 ns |
| PII scan, 4 KB with no PII | 10.5 µs |
| PII scan, 4 KB containing PII | 15.3 µs |
| PII scan of a full HTTP exchange (path, headers, bodies) | 1.75 µs |

The regex prefilter costs about 2.5 µs per KB on clean text, so the scan cost
grows with payload size.

## 5. Fuzzing

The fuzzing harness is in `fuzz/` (libFuzzer via `cargo fuzz`, nightly). It has two targets:

- **`parsers`** feeds arbitrary bytes, split into packets in both directions
  and including capture gaps, to every protocol parser.
  - First run: 103 crashes, all from an unbounded allocation in the Redis
    parser driven by an attacker-chosen array length. That bug is fixed.
  - Since the fix: 16.8M executions across two runs with 0 crashes. The
    second run was after the HTTP/2 rewrite, with 3,501 coverage edges.
  - After the Kafka, AMQP and DNS rewrites: 3.3M executions in 240 s, 0
    crashes.
- **`detect`** runs protocol detection and direction inference: 91M
  executions and 0 crashes.

## 6. Known limits found while measuring

- **MySQL 8 clients use TLS by default.** That is why MySQL recall was 0% on
  the wire before; the oracle disables TLS to test the parser. On real
  deployments MySQL plaintext comes from the OpenSSL uprobes, which are
  validated with HTTP (above) but not yet with a MySQL client.
- **HTTP/2 joined mid-connection** (agent started after the connection was
  opened): HPACK state is lost, so most headers, including the path, cannot be
  decoded until a new connection is opened.
- **Large capture gaps in HTTP/2** (several frames lost) reset that
  connection's parser. Gaps inside a single DATA frame are handled. Over TLS a
  gap only occurs past 16 KB per read/write call.
- **Per-packet capture is truncated at 4 KB** (16 KB per TLS read/write, in
  four events). Larger messages are reassembled where the protocol allows it. `panopticon_capture_truncated` counts what was
  cut.
- **TLS addresses are learned on the connection's first socket I/O inside a
  hooked call.** Until then, and on kernels where neither the sock tracepoints
  nor fentry/kprobes are available, TLS exchanges are exported without
  addresses and are left out of the service graph.
- **Statically linked TLS** other than Go (BoringSSL in Envoy, rustls, Java)
  is not covered, nor are Go binaries stripped of their symbol table.
- **Kafka is recognised by port 9092 only** (no magic bytes); brokers on other
  ports are not parsed. Compressed record batches (gzip, snappy, lz4, zstd)
  are framed and scored for topic and status, but their records are not
  decoded, so PII inside them is not visible. Each messaging protocol is
  scored against one server implementation (Kafka 3.8, RabbitMQ 3.13, a
  dnspython server).

## 7. Reproducing

Requirements: root on Linux 5.8+, a release build
(`cargo build -p panopticon-agent --release`), Docker for the database and
messaging runs, Python with `pip install pyroute2 redis 'psycopg[binary]'
pymysql mysql-connector-python cryptography grpcio confluent-kafka kafka-python
pika dnspython`, and Go for the load generator and the Go TLS oracle.

```bash
# HTTP/1.1 accuracy, kernel cost, agent CPU/RSS. Fails below 99% recall.
sudo tests/oracle/run.sh 2000 1234
sudo tests/oracle/run.sh 5000 42          # load run

# HTTPS through the OpenSSL and Go TLS uprobes (client and server views).
# Needs openssl and go.
sudo env PATH="$PATH" tests/oracle/run_tls.sh 1000 42   # OpenSSL and Go stacks

# Redis, PostgreSQL, MySQL, gRPC. Fails if any protocol is below 99% recall.
sudo tests/oracle/run_protocols.sh 500 7

# Kafka, RabbitMQ (AMQP 0-9-1), DNS. Fails below 99% recall or on any leak.
sudo tests/oracle/run_messaging.sh 500 7

# Sustained load: concurrency, duration, rate (0 = max), newconn (1 = one
# request per connection). Reports recall, drops by cause, CPU and RSS.
sudo tests/load/run_load.sh 64 20s
sudo tests/load/run_load.sh 64 30s 0 1

# User-space cost per event, one core: record a capture, then replay it
# (with your config; add --json-export /dev/null to include export).
sudo ./target/release/panopticon-agent -i eth0 --capture-raw /tmp/load.pncap
./target/release/panopticon-agent --replay-bench /tmp/load.pncap

# Micro-benchmarks
cargo bench -p panopticon-agent --bench parser_throughput --bench pii_regex --bench protocol_detect

# Fuzzing (nightly)
cd fuzz && cargo +nightly fuzz run parsers -- -max_total_time=600
```

Each runner exits non-zero if recall is below the minimum or if any raw PII
value appears in the export. The same three runs execute in CI on pull
requests (`.github/workflows/oracle.yml`, also runnable by hand from the
Actions tab).

If Python is installed in a virtualenv, point the runners at it with
`PYTHON=/path/to/venv/bin/python`. Benchmarks build with a stub eBPF object,
so rebuild the release agent before running the oracles again.
