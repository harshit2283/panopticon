## 2. Capture accuracy (ground truth)

Every request is generated by an oracle that logs what it sent and what came
back (`truth.jsonl`). Each request carries a unique token, and a scorer matches
the agent's JSONL export against the truth file. The scorer reports the
following:

- **recall**: share of real exchanges the agent exported;
- **duplicates / phantoms**: exports that match no exchange, or match one twice;
- **field accuracy**: method, status, response size, path;
- **PII visibility**: share of requests that carried PII (emails, SSNs and
  cards in bodies, query parameters and SQL literals) that the agent flagged;
- **leaks**: raw PII values found anywhere in the export. This must be zero.

### HTTP/1.1

`tests/oracle/run.sh`: keep-alive connections of up to 6 requests; GET, POST
with a JSON body containing an email and an SSN, chunked responses, and
bodies from 0 B to 12 KB (more than one 4 KB capture slot).

| Run | Exchanges | Recall | Dups / phantoms | Status / method | Response size | POST bodies captured / redacted | Leaks |
|---|---|---|---|---|---|---|---|
| Before this release (seed 1234) | 2,000 | 8.2% | — | — | — | — | — |
| Current, seeds 1234, 7, 99, 42, 77 | 2,000 each | 100% | 0 / 0 | 100% | 99.8–99.9% | 100% / 100% | 0 |
| Current, load run, seed 42 | 5,000 | 100% | 0 / 0 | 100% | 99.9% | 1,008 / 1,008 | 0 |

Recall is 100% at every keep-alive position (1st through 6th request). The
response-size misses are all large chunked responses where some packets were
lost from capture. The exchange is still exported and the size is
under-reported.

### HTTPS, Go `crypto/tls`

`tests/oracle/run_tls.sh` (go stack): a Go `net/http` client and server
(`go_tls_oracle.go`, HTTP/1.1 over TLS, keep-alive, GETs up to 70 KB and POSTs
with an email and an SSN). Writes are hooked at `(*Conn).Write`. Reads use
an entry probe plus a uprobe on every `RET` instruction of `(*Conn).Read`,
keyed by goroutine, because uretprobes break when Go moves goroutine stacks.

| Run | Exchanges | Recall (client / server view) | Status / method / size | With socket addresses | Leaks |
|---|---|---|---|---|---|
| Before (writes only, PID-scoped probes) | 300 | 0% / 0% | — | — | — |
| Current, seed 42 | 500 | **100% / 100%** | 100% / 100% / 100% | 100% / 99.6% | 0 |
| HTTP/2 (`go-h2` stack), before | 300 | 55–65% / 55–65% | — | — | 0 |
| HTTP/2 (`go-h2` stack), current, seeds 7, 14, 42 | 300–500 | **100% / 100%** | 100% / 100% / 100% | 100% / 100% | 0 |

Repeated runs of the HTTP/1.1 stack (seeds 42–51, ten runs per build, on
64 vCPUs) are not always clean. In 2 runs of 10, the client view scores
99.8%: one exchange in 500 is missing, and its neighbours on the same
connection are paired with the wrong responses. The server view stays at
100%, and no events are dropped. The build before the ring sharding
behaves the same (also 2 of 10), so this is not new. The cause is not
established yet.

HTTP/2 over TLS had two problems of its own:

- **Connection keys were reused.** Go and OpenSSL reuse the memory of a closed
  connection object, so a new connection can get the same `*tls.Conn` /
  `SSL*` key. Its preface then landed in the old connection's parser, along
  with its stale HPACK state. A client preface now restarts the parser.
- **Large reads and writes were cut.** One TLS read or write often holds a
  whole 16 KB record, which is several frames, while each event carries at
  most 4 KB. The probes now emit a call as up to four consecutive 4 KB events,
  so parsers see the stream contiguously.

Before this fix, the client process was not hooked at all. The probes were
PID-scoped, and a second process running an already-hooked binary was
skipped. Every replica of a Go service on a node was affected. Probes now
cover every process that runs the binary, as they do for `libssl`. POST
bodies are cut at `max_body_bytes` (4 KB). Go's JSON encoder sorts keys
(`email`, `note`, `ssn`), so in the 5 KB POSTs the SSN falls past the cut and
is never exported. Earlier runs counted those bodies as unredacted ("PII
redacted in 75/117", against 110/110 for CPython, whose `json.dumps` keeps
`ssn` before `note`). That was a scorer artifact, not a detection gap: no raw
value reached the export. `score.py` now reports such bodies as "cut at
max_body_bytes before a PII value" instead.

### HTTPS (OpenSSL uprobes)

`tests/oracle/run_tls.sh`: the same HTTP/1.1 mix over TLS on loopback,
generated by CPython, which uses the system OpenSSL 3.0 (`SSL_read_ex` /
`SSL_write_ex`). The uprobes see both ends, so each exchange is exported once
from the client process and once from the server process, and each view is
scored on its own.

| Run | Exchanges | Recall (client view / server view) | Dups | Status / method / size | With socket addresses | POST bodies redacted | Leaks |
|---|---|---|---|---|---|---|---|
| Before this release | 300 | 0% / 0% | — | — | 0% | — | — |
| Current, seed 42 | 1,000 | **100% / 100%** | 0 | 100% / 100% / 100% | **100% / 100%** | 197 / 197 per view | 0 |

There were two causes of the 0%:

- Only `SSL_read`/`SSL_write` were hooked, while OpenSSL 1.1.1+ applications
  (CPython, curl, recent nginx) call the `_ex` variants.
- TLS connections were keyed per thread, with the direction relative to the
  process. So server processes had requests parsed as responses, and
  connections interleaved on one event-loop thread were mixed together.

Connections are now keyed on the library's `SSL*`, and the client/server role
is inferred from the first payload. Socket addresses come from the
`sock:sock_send_length` / `sock_recv_length` tracepoints firing inside a
hooked TLS call (fentry or kprobes on older kernels, not validated here: this
VM has kprobes compiled out and kernel lockdown blocks fentry).

Response sizes are exact even for 70 KB bodies, because each `SSL_read` /
`SSL_write` buffer beyond 4 KB is accounted for as a gap, which the parser
skips.

### Kafka, AMQP (RabbitMQ), DNS

`tests/oracle/run_messaging.sh`: a fresh agent per protocol. Every operation
puts its token in the record key/value, routing key, message body or query
name; bodies carry an email. Besides the operations themselves, the truth
includes every record a consumer received back, so 500 operations give
about 740 Kafka and 910 AMQP truth entries.

| Protocol | Traffic mix | Recall before → now | Field accuracy now | PII visibility before → now | Leaks |
|---|---|---|---|---|---|
| Kafka 3.8 | librdkafka Produce v10 (single records with and without headers, multi-record batches, `MESSAGE_TOO_LARGE` rejections), kafka-python Produce v8, concurrent consumer (Fetch v16, topic IDs), Metadata v1/v4/v9/v12 for missing topics | 0% → **100%** | topic, API, error code 100% | 0% → **100%** | 0 |
| RabbitMQ 3.13 | Basic.Publish to topic, fanout, direct and default exchanges, publisher confirms, 6 KB bodies, unroutable mandatory publishes (Basic.Return 312), Basic.Get (also on missing queues: 404), Basic.Consume deliveries, Basic.Ack | 43.7% (Get, Return 0%) → **100%** | method, exchange/routing key or queue, reply code 100%; client acks 372/372 | 0% → **100%** | 0 |
| DNS | A, AAAA, CNAME chains, NXDOMAIN, SERVFAIL, TXT; 10% over TCP | 90.2% (TCP 0%) → **100%** | query name, type, rcode, answers 100% | — | 0 |

Measured with seed 7 (500 operations) and seed 42 (1,000 operations, also
100% everywhere, 0 duplicates). What was wrong before:

- **Kafka**: the topic was read at a fixed offset, wrong for every version
  current clients send (Produce v3+ starts with `transactional_id`; v9+,
  Fetch v12+ and Metadata v9+ use compact encodings and tagged fields;
  Fetch v13+ names topics by ID), so no exchange had a topic. Records were
  never decoded, so produced and fetched values (and the PII in them) were
  invisible. The error code was read at a fixed offset (Produce responses
  reported values like 29284). Requests and responses were exported
  separately. A Fetch response larger than the 256 KB buffer closed the
  connection's parser, and a capture gap reset it.
- **AMQP**: message bodies were never read, Basic.Get and GetOk were
  unrelated records with no queue or body, a Basic.Get on a missing queue
  showed no error, Basic.Return had no reply code, and every method frame
  (Channel.Open/OpenOk/CloseOk...) was a record of its own. A capture gap in
  a large message desynchronised the stream.
- **DNS**: queries and responses were exported as two records, the rcode
  only on the second; DNS over TCP (length-prefixed) was not parsed; AAAA
  answers were not in canonical form (`fd00:0:0:0:0:0:0:2a`).

Exchanges are now one record each, exported at the response (Kafka, DNS,
AMQP synchronous methods), or when the message content is complete (AMQP
publish, deliver, return). IPv4 answers in DNS records are redacted to
`<IP_V4>` by the default PII policy.

## 3. PII detection accuracy

Capture accuracy above shows that PII reaches the scanner. This section shows
how well the scanner tells PII from look-alikes. The detector measured is the
default build: regex patterns with validation. ONNX/ML inference is
feature-gated (`--features ml`), off by default (`pii.mode` is `Disabled`),
and no model ships in `models/`, so names and addresses are not measured (see
below).

### Method

- **Corpus**: `tests/pii/gen_corpus.py` (seed 20261104) writes
  `tests/pii/corpus.jsonl`: 5,000 payloads, 70% clean. Each one is a single
  agent field: JSON request and response bodies, form bodies, query strings,
  HTTP header values, SQL text, Redis arguments and log lines. Every PII value
  has a label with its exact type and byte span.
- **Types**: email; phone (US, international, India `+91`, `0` and bare
  10-digit); credit card (Luhn-valid, real issuer prefixes, RuPay
  included); US SSN; Aadhaar (Verhoeff-valid, first digit 2–9); PAN; UPI ID;
  GSTIN (valid check character); Indian passport; IBAN (valid mod-97);
  IPv4; JWT; API key; AWS access key.
- **Hard negatives**: most clean payloads are full of values that look like
  PII: order and transaction IDs, UUIDs, ISO timestamps, Unix epochs in
  seconds and milliseconds, 12-digit numbers that fail Verhoeff, 16-digit
  numbers that fail Luhn, version strings, user agents, OIDs, prices, SKUs,
  base64 blobs, hex hashes, `logo@2x.png`, `lodash@4.17.21`, and PAN, GSTIN,
  IBAN and passport look-alikes that fail their checks or have no context.
- **Policy decisions**: every IPv4 address counts as PII, because client
  addresses are personal data under GDPR and India's DPDP Act, and a passive
  observer cannot tell a client from a server. Emails at `example.com` count
  as real emails: test accounts use them, and so do the capture oracles.
- **Scoring**: `pii::accuracy` (a `cargo test`) puts each sample in its
  `L7Message` field and calls `PiiEngine::scan_message`, the call the event
  loop makes, with the default config. A finding is a true positive if it
  overlaps a label of the same type. The three phone categories are scored as
  one family. Values in credential headers (`Authorization`, `Cookie`,
  `X-Api-Key`, …) are masked wholesale without detection, so they count only
  for the redaction check. The redaction check asserts that, after the call,
  no labelled value is still present in the field.
- **Caveat**: the same corpus was used to tune the patterns and to score
  them, and the hard negatives are only as varied as the generator. Read the
  numbers as a regression baseline, not as accuracy on your own traffic.

"—": nothing detected. GSTIN, IBAN, passport and UPI had no pattern before.
"Before" is commit `5d7194b`.

What changed (`panopticon-agent/src/pii/regex_prefilter.rs`, `validate` and
`RegexPrefilter::scan`):

- **Aadhaar**: Verhoeff check digit, first digit 2–9, and not one group of a
  longer grouped number (`continues_digit_group`). Before, any 12 digits
  matched, including the first 12 of a spaced card number.
- **Credit card**: Luhn plus a real issuer prefix and length
  (`card_iin_valid`). Millisecond epochs pass Luhn one time in ten.
- **PAN**: the 4th character must be a holder type (P, C, H, F, A, T, B, L,
  J, G).
- **Phones**: US numbers follow NANP (area and exchange codes start with
  2–9). A US number without separators or `+1`, and an Indian mobile
  without `+91` (`9876543210`), counts only after a phone keyword (`phone`, `mobile`, `msisdn`, `tel`,
  `contact`, …) with no other number in between (`has_context`). Before,
  every 10-digit ID and epoch was a US phone number. A new `PHONE_IN`
  category covers `+91`, `0`-prefixed and bare Indian mobiles.
  International numbers need 8–15 digits, and all their groups are consumed.
- **IPv4**: not part of a longer dotted run (`1.3.6.1.4.1…` OIDs).
- **Email**: not an image or script asset name (`logo@2x.png`).
- **New**: `UPI` (a VPA with a known bank handle), `GSTIN` (check
  character), `IBAN` (mod-97), `PASSPORT_IN` (needs the word "passport"
  just before it).
- **One finding per value**: overlapping candidates resolve to the longest,
  so a GSTIN is not also reported as a PAN.

`cargo test` fails if any type drops below its precision or recall floor, if
more than 1.25% of clean payloads produce a finding, or if more than 60
labelled values survive redaction (`GATE` in `pii/accuracy.rs`).

Cost (`cargo bench --bench pii_regex`, Apple M-series laptop, medians,
before → after): 4 KB with no PII 6.01 → 5.87 µs, 4 KB with PII 9.25 →
9.33 µs (no significant change), full HTTP exchange 850 → 918 ns (+7%).

### What it still misses or over-reports

- **No context, no detection**: a bare phone number or passport number with
  no keyword just before it (a log line `user 9876543210 verified`, or a
  positional SQL `INSERT … VALUES (…)` list where the column name is far
  away). These make up all of the remaining phone, passport and API-key
  misses.
- **PAN-shaped codes**: product codes such as `PRDPF6402A` are
  indistinguishable from a PAN and are flagged.
- **Every IPv4 address** is flagged, by the policy above.
- **Bare 10-digit numbers after a phone keyword** are reported as `PHONE_IN`,
  even when they are US numbers.
- **Names, street addresses, dates of birth**: only the ML path could find
  them. To measure it: build with `--features ml`, install ONNX Runtime
  1.19.2+ (`ORT_LIB_LOCATION`), download the ~265 MB DistilBERT-NER model
  (`scripts/download_model.sh`) and set `pii.mode` to in-agent with its
  `model_path`. The corpus has no name or address labels yet.
- **Past `max_body_bytes`** (4 KB by default) nothing is scanned or exported.
  A value cut in half at the boundary is exported in part and not
  recognised.

## 4. Overhead

### Kernel (per captured packet)

The kernel runtime of the TC classifier (the default backend) is measured
with `kernel.bpf_stats_enabled=1`, reading `run_time_ns / run_cnt` from the
program's fdinfo (`tests/oracle/bpf_cost.py`). This is the time the kernel
spends in Panopticon's eBPF program for each packet on the monitored
interface. It is not end-to-end latency. The `cgroup_skb` backend runs at
every local socket instead, so its cost per request differs; see
[cgroup_skb capture backend](#cgroup_skb-capture-backend-preliminary).

| Path | ns / packet |
|---|---|
| Before this release | 12,500–15,000 |
| Current, TCP packet with payload (captured) | 1,200–2,000 |
| Current, packet that is not captured (e.g. ICMP) | ~85 |
| Under sustained load (~40K packets/s), before the wakeup fix | 6,643 |
| Under sustained load (~40K packets/s), current | 1,600–1,700 |
| 64 vCPUs, 1K-4K connections, one shared ring (before sharding) | 14,000–17,900 |
| 64 vCPUs, 1K-4K connections, sharded rings (current) | 695–716 |

With TLS capture on (`tls_scan_enabled`, the default), two more hooks run on
**every TCP send and receive on the node**, not only TLS ones, to learn TLS
connections' addresses. They cost 80–300 ns per call on this VM (about 80 ns
under sustained load), against ~100 ns for an empty program on the same
hooks. Turn TLS capture off to remove them. The same hooks run with the
`cgroup_skb` backend (in its scoped modes as fentry programs that check the
socket's scope); there they measured 22–82 ns per call on five kernels.

Two changes account for most of the gain. The payload is now copied with one
`bpf_skb_load_bytes` instead of byte by byte. Ring-buffer wakeups are now
batched, where previously every event woke user space, which was about 90% of
the cost.

### Agent (user space)

These figures come from `tests/oracle/run.sh 5000 42`. The generator is a
single Python client, so it produces about 39 exchanges/s (21K events). That
measures cost per event and memory under sustained traffic; **it is not a
throughput ceiling**.

| | Before | Current |
|---|---|---|
| Agent CPU over the run (128 s) | 7.61 s (5.9% of one core) | **2.98 s (2.3%)** |
| Peak RSS | 367 MiB | **122 MiB** |
| Idle CPU (no traffic) | 4.4% of one core | **1.0%** |
| Idle steady-state RSS | 88 MiB | 56–90 MiB |

Most of the old peak came from the TLS library scanner reading every
executable on the host whole into memory, and most of the old idle CPU came
from a fixed 2 ms ring-buffer drain tick. Both are fixed: the scanner reads
only ELF headers and symbol tables, and the tick backs off to 16 ms while
idle and returns to 2 ms as soon as events arrive.

### Sustained load and connection churn

`tests/load/run_load.sh` drives HTTP/1.1 through the same veth topology with
a Go load generator (`tests/load/loadgen.go`), and reports the achieved
rate, capture recall, drops by cause, agent CPU and peak RSS. The VM has 4
vCPUs shared by the load generator, its server and the agent, so the rates
below are limited by the generator, not by the agent.

64 keep-alive connections, as fast as possible, 512 B responses, 20% POSTs
with an email in the body (`run_load.sh 64 20s`):

| | Before | Current |
|---|---|---|
| Achieved load | 17.7K req/s | 21.7–23.1K req/s |
| Capture recall | 97.35% | 99.99–100% |
| Events dropped | 2.5% (worker queues full) | 0–0.01% |
| Kernel TC cost per packet | 7,453 ns | 1,599–1,693 ns |
| Agent CPU | 78% of one core | 58–60% |
| Peak RSS | 224 MiB | 97–101 MiB |

Large responses, 200 KB bodies over 200 connections
(`run_load.sh 200 20s 0 0 200000`, about 1.8 GB/s through the veth):

| | Before | Current |
|---|---|---|
| Achieved load | 7.5K req/s | 9.1K req/s |
| Capture recall | 43.9% | 98.0–98.3% |
| Drops (kernel / workers / export) | 90K / 34K / 63K | 0–16K / 0.5–16K / 0 |
| Agent CPU | 116% of one core | 60–64% |
| Peak RSS | 233 MiB | 114–137 MiB |

Before, every exchange carried up to 64 KB of body text through PII
scanning, the export queue and the JSON writer. Bodies are now cut to
`max_body_bytes` (default 4 KB) before any of those stages, so the
redaction still covers everything that is exported. The remaining drops
come in bursts, while the load generator saturates the VM's 4 vCPUs.
On this 4-vCPU VM, running the ring buffer drain on its own thread (also
tried at raised priority) did not reduce them measurably. On 64 vCPUs the
single drain thread was the limit, and the ring is now sharded and drained
by one thread per shard (see [64-vCPU scale test](#64-vcpu-scale-test)).

Connection churn, one request per TCP connection (`run_load.sh 64 30s 0 1`):
8.4K connections/s with 99.98% recall. Tracked connections stay at 0–36,
because the parser state of a connection is dropped on its FIN/RST. Before
that, about 14K stale entries waited for the 30 s idle timeout, and heavier
churn would have hit the 65,536-entry table limit and evicted live
connections. The service graph stays at one edge, where it used to gain a
node and an edge per client connection.

### Where the CPU goes

`--replay-bench FILE` runs a raw capture (`--capture-raw`) through the same
worker code as live traffic, on one core, without the kernel or scheduling
noise. Here it is the 64-connection load above (43K events):

| Pipeline | Before | Current | Events/s on one core |
|---|---|---|---|
| Parse only (PII and graph off) | 3.46 µs/event | 1.5–1.7 µs | ~600K |
| Parse + PII + graph | 6.25 µs | 4.5–4.8 µs | ~210K |
| Parse + PII + graph + JSON export | 14.64 µs | 6.5–7.6 µs | ~150K |

The biggest gains came from three changes:

- **Allocator.** glibc's malloc arena locks were about 20% of busy samples,
  because workers allocate messages that the export thread frees. The agent
  now uses mimalloc.
- **JSON export.** It used to flush and `write(2)` after every exchange.
- **Graph templates.** Every request with a unique query string became its own
  graph template, which cost memory as well as CPU.

Live, the agent spends about 15 µs of CPU per event at this load. The
difference from the replay figure is the kernel-to-user hand-off and
contention for the VM's 4 vCPUs. Plan on roughly one core per 60K
captured packets per second with JSON export on.

Not measured yet: kernel-to-export latency percentiles, and memory with the
ONNX model loaded. Kernel-to-worker latency is measured, in an experiment
build, in the [scaling study](#scaling-study-and-fixed-rate-overhead-preliminary).

Two bottlenecks were measured:

- **Ring reserve lock.** On the load CPUs, `bpf_ringbuf_reserve` →
  `resilient_queued_spin_lock_slowpath` took 23% of all CPU, mostly from
  `tc_egress`. Every producer on the node serialised on the one ring's lock.
- **The drain copied whole events.** Each event was read, rebuilt and moved
  as a full 4,160-byte struct on one thread. glibc memmove was 15-21% of
  agent samples.

**What changed:**

- **Sharded ring.** `DATA_EVENTS` is now 16 rings. The loader activates a
  power of two of them, one per 4 online CPUs (16 here, 2 on 8 vCPUs), and
  splits 16 MiB across the active ones.
- **Sharded by connection, not by CPU.** A connection's packets are
  produced on whichever CPUs its threads and softirqs run on, so CPU shards
  would let user space see a response before its request. Sharding by the
  connection cookie puts every event of one connection in one ring: both
  directions, its connect/accept owner events, and its FIN/RST (all carry
  the same 5-tuple cookie), or one TLS connection object. So the order seen
  per connection is that ring's reserve order, exactly as with one ring.
- **TC records at captured size.** TC builds the event in the per-CPU
  scratch map and copies the header plus the captured bytes into the ring,
  instead of reserving a fixed 4,168-byte record. TLS events keep
  fixed reserves, because a uprobe can be preempted mid-event and a shared
  scratch slot would be overwritten; connect/accept events are the header
  only. (The `cgroup_skb` backend reserves each packet at a payload size
  class instead; see its section below.)
- **One drain thread per shard.** Draining has its own threads (woken by
  edge-triggered epoll or the 2 ms tick), not the tokio main loop. Each
  event is copied once, at header plus `payload_len`, into packed worker
  batches of up to 64 events or 64 KB. Each drain thread feeds its own
  subset of the workers, so a worker's channel takes full batches from one
  producer.
- **Bigger worker channels.** The default `worker_channel_capacity` is now
  4,096 events (was 1,024), to absorb a shard drained in one burst. With
  1,024, the 4K row lost 5% of events to full channels while the workers
  were half idle.

  the limit.

  run in 5, with or without this change (2 of 10 runs each), with no drops.

### Scaling study and fixed-rate overhead (preliminary)

**Preliminary.** One VM on a shared host, measured on one day (2026-11-04).
The key comparisons have three runs per cell; most matrix cells have one. The
experiment builds are not merged. The raw per-run outputs, perf reports and
the scripts that produce every number below are kept with the study notes, so
each figure can be recomputed.

**Question.** The 64-vCPU rows above give agent CPU per event. Doubled to per
request, that is about 13 µs at 64 connections and 46 µs at 4K. Those rows
were closed-loop runs at different rates, though: about 70K req/s at 64
connections and 220-265K req/s at 4K. They mixed request rate with connection
count, so this study holds the rate fixed and tests five explanations, one
change at a time.

**Rig.** As in the 64-vCPU scale test:

- **VM.** 64 vCPUs and 64 GB on kernel 7.0, on an AMD Threadripper PRO 9995WX
  host. The vCPUs are not pinned to host cores.
- **Pinning.** The agent runs on CPUs 0-15 (16 workers). The load generator,
  server and veth softirqs run on CPUs 16-63.
- **Agent config.** The rate limiter is lifted the same way in every run
  (`max_events_per_sec = 100000000`).
- **Load.** 512 B responses, 20% POSTs with an email address in the body,
  20 s per run.

**Method.**

- **Fixed rate.** `loadgen.go -rate N` now paces each connection on its own
  schedule. The old shared ticker dropped ticks at high rates. Every cell
  reports achieved against target, and a miss over 2% makes the cell invalid.
  No fixed-rate run in this study missed by more than 0.18%.
- **Agent CPU.** `utime + stime` of the agent over the load plus a 3 s drain.
  It is divided by the requests the client completed (µs/req) and by the load
  duration (cores).
- **Recall.** Requests found in the JSON export divided by requests completed.
- **Recall proxy.** Without the export, recall uses a proxy. The scanner finds
  one PII entity per request (the IP address in `Host`) plus the email in
  every 5th request, so `pii_detections / (requests + POSTs)` estimates the
  share of requests that were parsed and scanned. It reads exactly 100% when
  nothing is dropped. Export drops happen after the scan, so the proxy cannot
  see them.
- **Application slowdown.** The same cell is run without the agent
  (`NO_AGENT=1`). The comparison uses client service latency (request sent to
  last byte) and the server process's CPU per request.
- **Discard rule.** A run is discarded if mean steal in either CPU set is over
  1%, or if other tenants' load is over 40. Other tenants' load is the host's
  1-minute load minus this VM's busy vCPUs. One run was discarded and repeated
  (no agent, 64 connections, 20K req/s, 1.06% steal). As first written, the
  rule used raw host load, which counts this VM's own vCPU threads. That would
  have dropped 7 high-rate matrix runs whose steal was below 0.1%, so the rule
  was corrected to other tenants' load. No other run is affected under either
  version. The thresholds were set during the study; they are not in the
  predictions written before it.
- **Run order.** Builds were interleaved in a fixed, repeated order, not a
  randomized one. The combined builds in stage 2 ran later than the stage 1
  baseline, without baseline runs of their own alongside them.
- **Experiments.** Each experiment is a compile-time switch in one source
  tree, so the baseline binary is built from that same tree. The baseline
  differs from the release code in one way: the JSON export moved after the
  service graph, so that H3 can move the message into it. That move is
  expected to be cost-neutral; it was not measured separately.

**Finding 2. The steep part comes from one call, `DashMap::len()` in the
service graph.** `EdgeAggregator::record` (`graph/aggregator.rs`) compares
`current_window.len()` with `MAX_FLOWS_PER_WINDOW` on every request.
`DashMap::len()` read-locks and unlocks each of the map's 64 shards. That makes
about 128 atomic read-modify-writes per request, on lock words shared by all
16 workers. Every worker also write-locks the one shard that holds the hot
flow key.

A frame-pointer profile at 4K connections and 150K req/s shows:

| `DashMap::len()` inside it | 49% of agent CPU |
| `record_with_server` self time on the shard read-lock and unlock lines (`perf annotate`, `dashmap/src/lock.rs:61` and `:70`) | 91% |
| `lock_shared_slow` | 6.5% of samples, 5.5 points of it from that `len()` |
| `lock_exclusive_slow` | 0.5%, from the same function's `entry()` |
| `len()` at 20K req/s | 4.9-5.7% of agent CPU |

how many workers run at the same time, which means with the request rate.

earlier version of *Where the time goes now* above blamed these samples on the

#### Fixed-rate overhead matrix (baseline build)

This is the overhead to publish: the baseline build at fixed rates. That build
is the release code plus the cost-neutral sink reorder described under Method.

- **Modes.**
  - **(a1)** `metrics_only`.
  - **(a2)** `redacted` with the JSON export off. In the measured build
    `sampling_mode` and `sample_rate` were parsed but not acted on, so
    "export off" stands in for "export sampled".
  - **(b)** `redacted`, every request exported.

#### Kernel → worker latency

so each bucket is about 19% wide, and the table shows bucket upper bounds.

#### Recommendations, ranked by measured gain per line changed

1. **Replace `DashMap::len()` in `EdgeAggregator::record` with an atomic flow
   count.** About 10 lines. At 4K connections and 150K req/s, µs/req falls
   from 35.9 to 15.9 (-56%). Other cells: -7% at 64×50K and -5% at 4K×20K.
   Do it together with item 4.
2. **Stop cloning each message (H3).** About 25 lines: take the parser's
   messages by value, redact in place, and move them into the JSON export as
   the last sink. Saves 5-7% (-6.3% at 4K×20K; -6.8% on top of the item 1 fix
   at 150K). Items 1 and 2 together ("win") measured -8 to -14% at 20-50K
   req/s and -62% at 4K×150K.
3. **One `RegexPrefilter` per worker (H1).** About 10 lines. It is only worth
   it on top of item 1: -12.8% at 4K×150K, but +4.6% (within noise) at
   64×50K. It removes the lazy-DFA rebuilds that the shared cache pool causes
   (`determinize::*` falls from 6.7% to below the top 60 symbols). Ship it
   only with a high-rate benchmark that keeps it honest.
4. **Size the JSON export queue for bursts.** It is a fixed 4,096 events with
   a 5 ms poll. Once item 1 lands, it is the first thing to drop data at high
   rates (1.1-1.7% of exports at 150K req/s). Not measured here.

**Not recommended, because the data did not support them:**

- **Per-worker aggregators (H2-shard).** No gain over the item 1 fix,
  with more code and memory.
- **Per-thread identity memo (H2-id).** No effect in either stage.
- **Per-connection state layout or prefetching for cache misses (H4).** The
  miss counters did not move between 64 and 4K connections.
- **Moving PII scanning off the hot path to save connection-scaling cost
  (H5).** The scan cost does not depend on connection count. It is about
  3 µs/req at fixed rates up to 50K. Its growth at high rates is the regex
  pool (item 3).

#### Caveats

- **Shared host.** This is one VM on a shared host, and the vCPUs are not
  pinned to host cores. The guest reports a meaningless L3 topology (one
  "1 GiB" instance per vCPU), so cache effects across the host's 12 CCDs are
  uncontrolled.
- **Load during the study.** Mean steal stayed at or below 0.36% in every
  kept run (304 of 305). Other tenants' load rose from about 8 to about 31
  during the matrix runs.
- **Counters.** `LLC-loads` and `LLC-load-misses` are not supported in the
  guest. `cache-misses` and `cache-references` are AMD's generic events, which
  may not count cross-core (coherence) transfers. Those transfers are exactly
  what the `len()` contention generates, and they may be where the +15% user
  cycles at 4K go (H4). The 7-event `perf stat` set was multiplexed (about 85%
  enabled), so the user/kernel split was repeated with 6 events and no
  multiplexing.
- **Profiles.** DWARF call graphs (`--call-graph dwarf`) did not unwind the
  agent's user stacks in this VM, though they worked for other binaries. The
  call-graph attribution therefore uses a build with frame pointers
  (`-C force-frame-pointers=yes`). That build is used for attribution only and
  never timed. Its µs/req at 150K (34.3) matched the baseline's.
- **Rate vs connections.** 64 connections cannot reach 150K req/s on this
  rig, so the steep part of the curve is measured at 4K connections only.
  At the same 100K rate, `len()` costs far more with 4K connections than with 64: the fix takes 4K from 24.4 to 13.7 µs/req and 64 from 12.6 to 11.5. Why more workers contend at the same rate when there are more connections was not measured. One candidate is that 4K connections spread the work more evenly over the 16 workers, so more of them are in `record()` at once.
- **Recall proxy.** Modes (a1) and (a2) use the PII-count recall proxy, which
  cannot see export drops (there is no export in those modes).
- **Repetition.** Matrix cells outside mode (b) are single runs.
- **Equal work.** At 4K×150K the faster builds drop 1-2% of exports
  (export queue full) where the baseline drops almost none, so their µs/req
  covers slightly less export work.
- **Untested.** The loadgen's latency from the *scheduled* send time includes
  up to about 0.5 ms of Go timer slop at low rates, so the tables use service
  time instead. The ONNX model path and TLS traffic were not tested.

### cgroup_skb capture backend (preliminary)

**Preliminary.** Measured on 2026-11-10 on lab VMs on a shared host, against
the TC backend in the same runs. `[capture] backend = "cgroup_skb"` is not
the default. Raw per-run outputs are kept with the study notes.

The `cgroup_skb` backend attaches to the root of the cgroup v2 hierarchy, so
it runs at every local socket on the node: both ends of a node-local
connection, loopback included (with `capture_loopback = true`; dropped
by default), which TC on an interface never sees. Scope
(`pid_filter`, `cgroup_filter`, `sampling_mode`) is decided in the kernel per
socket, and always-on hooks keep the per-socket state: `cgroup/sock_create`,
`sockops`, fexit `inet_csk_accept`, and the kTLS key-install markers on
`setsockopt`.

**Rigs.**

- **Kernel cost, five kernels.** 7.0 (32 vCPUs), and 4-vCPU VMs on 6.8, 5.15,
  RHEL 9 (5.14) and RHEL 8 (4.18). `tests/load/run_load.sh` at a fixed 5K
  req/s over 64 keep-alive connections, or 1K new connections/s.
- **Sustained load.** The 7.0 VM: 32 vCPUs and 32 GB, the agent pinned to
  CPUs 0-7 and the load generator, server and softirqs to 8-31. The rate
  limiter is lifted, and the JSON export is on (privacy mode `redacted`)
  unless noted. This is not the 64-vCPU rig above, so the absolute numbers do
  not compare with those tables.

**Method.**

- **Topology.** As in §1: the client in its own network namespace, the server
  on the host. The client's namespace is in the root cgroup, so the
  `cgroup_skb` backend sees both sockets of every exchange. Unscoped, it
  captures each exchange twice (two views). With `pid_filter` = the server
  (`SCOPE=server`), it captures the same server-side view as TC on the veth.
- **Kernel cost.** `tests/oracle/bpf_cost.py` per program, over the load
  window only (snapshot before, delta after). TC runs once per packet;
  `cgroup_skb` runs at both sockets, twice per packet of a node-local
  connection, in every mode. Compare per request.
- **Repetition.** Three runs per cell, in a fixed interleaved order. Figures
  are median [min-max]. Mean steal was at most 0.07% in every run.

**Findings.**

- **Scoped, it matches TC at 64 keep-alive connections.** `pid_filter`
  delivers TC's throughput, recall and agent CPU there (recall also with the
  listener before the agent; under connection churn it does not, see below). At 1K connections it cost about
  13% more agent CPU (4.07 against 3.61 cores) and dropped some events in
  the kernel ring; with compact records it uses less agent CPU than TC
  (3.41 against 3.70 cores) and drops none (see Compact records). The
  kernel spends about 0.9-1.0 µs more
  per request (1.4-1.7x TC's), and 1.8x at 4K connections opening at 20K
  req/s. The application does not measurably slow down.
- **Cutting in the kernel saves user space.** With `head_only`, the agent
  does almost nothing (0.01 cores against 0.22 on TC, where the cut is in
  user space), and the application runs faster than on TC.
- **Unscoped capture of node-local traffic doubles the work.** Both ends of
  every local connection are captured. That means twice the events, about
  twice the agent CPU, and, at 1K connections, export queue overflow
  (recall 84.7%; before compact records also 0.8-0.9M kernel ring drops).
  At 200 KB bodies, throughput is 13% below TC's.
- **Ring capacity.** Each packet record is reserved at the header plus the
  smallest power-of-two payload class (64 to 4,096 bytes) that holds the
  captured bytes, and a close record is the 96-byte header. Before that,
  every record was a fixed 4,168 bytes, and at 1K connections `pid_filter`
  lost 2.6-8.2K events in the kernel ring where TC lost none. Now it loses
  none (see Compact records).
- **`pid_filter` drops the bytes that arrive before `accept()` on a listener
  that predates the agent.** This is every server not restarted since the
  agent started, so it is the case after any agent restart. Such a listener
  has no recorded owner; a connection accepted from it is selected only once
  a listed process's `accept()` returns, and bytes before that are dropped
  (`no_owner`): 44% of requests under connection churn, and 0.5% at 4K
  connections opening at 20K req/s. With the server's listener created after
  the agent started (`SERVER_LATE=1`), the same cells measured 100% under
  the creator rule, the only rule then (now `pid_filter_listener =
  "creator"`); under the default `"acceptor"` every listener has the gap. In the
  runs above a whole keep-alive connection was also lost now and then (1 of
  64 in 6 of 27 runs): the kernel can hand a connection to `accept()` before
  its ESTABLISHED callback runs, and that callback cleared the recorded
  acceptor. That is fixed.

**`pid_filter` recall, listener before and after the agent** (7.0, 32 vCPUs,
n=3, median [min-max], after the `accept()` ordering fix, creator rule, now
`pid_filter_listener = "creator"`). `SERVER_LATE=0` is the server's listener
created before the agent, `SERVER_LATE=1` after:

| Cell | TC `pid_filter` | cgroup_skb, `SERVER_LATE=0` | cgroup_skb, `SERVER_LATE=1` | `no_owner` drops (cgroup_skb, `SERVER_LATE=0`) |
|---|---|---|---|---|
| New connection per request, 64 | 100% | **56.61%** [54.66-56.66] | 100% | 115.6K |
| 64 keep-alive, closed loop | 99.93% [99.92-100] | 100% [99.93-100] | 100% | 17 |

With keep-alive connections only the bytes before each connection's
`accept()` are lost, which is nothing once the connections are up; with a
new connection per request it is nearly half the requests. The remaining
keep-alive gaps are export queue drops (TC, and one cgroup_skb run), not
ownership.

The gap is by design: the agent does not infer an owner for a listener that
predates it, because it cannot prove which processes can accept on it (a
socket can be held through io_uring registered files, a queued
`SCM_RIGHTS` message or a kernel service, none of which `/proc` shows
completely). For full `pid_filter` recall on cgroup_skb, restart the server
after the agent and set `pid_filter_listener = "creator"`, or select by
`cgroup_filter` / `pod_filter`, which has no such gap.

- **No kernel ring drops left.** In four more runs of each `pid_filter`
  cell (another batch, after first), the kernel ring dropped 2.7-6.6K events
  per run at 1K connections before and none after. Records hold the header
  plus the captured bytes rounded up to a power of two (at least 64), so
  the rings hold many times more of them.
- **Cheaper in the kernel and in user space.** Kernel time per packet fell
  by 1-11% and agent CPU by 4-16%. Scoped at 1K connections the agent now
  uses less CPU than TC.
- **Clearing unused bytes.** Every byte of a reserved record is now written
  (the ring is mapped whole into user space and not zeroed between
  records), which costs one more helper call per packet: `pid_filter` at 1K
  connections, 531 [509-531] ns per packet run before and 556 [555-571]
  after (2.28 against 2.38 kernel µs per request), with no kernel drops,
  99.92% against 99.86% recall and 3.70 against 3.67 agent cores (n=3,
  same rig).
- **Out-of-scope sockets cost user space nothing.** Out of scope at 1K new
  connections/s, user space received 20,000 close records per 10 s run
  before and none after; the agent's CPU per request fell from 38 to 10 µs.
- **Recall.** The 98.43% and the unscoped export overflow are not from this
  change: one keep-alive connection (1 of 64) lost to `no_owner` in 2 of 3
  runs here, and 1 of 4 before and after in the second batch (the
  accept-before-ESTABLISHED race described above, measured before the owner
  fix); the export queue overflows the same way with both builds.

**Caveats.**

- **Rigs.** Lab VMs on a shared host (other tenants' load rose from about 4
  to 12 during the sustained runs). The sustained figures come from 32
  vCPUs, not 64, and the 6.8, 5.15, RHEL 9 and RHEL 8 cells from 4-vCPU
  VMs.
- **Two views.** For unscoped `cgroup_skb`, recall counts a request found in
  either view, and the agent exported about twice the records.
- **Not measured.** TLS traffic under load and the ONNX model.

## 6. Fuzzing

The fuzzing harness is in `fuzz/` (libFuzzer via `cargo fuzz`, nightly). It has two targets:

- **`parsers`** feeds arbitrary bytes, split into packets in both directions
  and including capture gaps, to every protocol parser.
  - First run: 103 crashes, all from an unbounded allocation in the Redis
    parser driven by an attacker-chosen array length. That bug is fixed.
  - Since the fix: 16.8M executions across two runs with 0 crashes. The
    second run was after the HTTP/2 rewrite, with 3,501 coverage edges.
  - After the Kafka, AMQP and DNS rewrites: 3.3M executions in 240 s, 0
    crashes.
- **`detect`** runs protocol detection and direction inference: 91M
  executions and 0 crashes.

## 7. Known limits found while measuring

- **MySQL 8 clients use TLS by default.** That is why MySQL recall was 0% on
  the wire before; the oracle disables TLS to test the parser. On real
  deployments MySQL plaintext comes from the OpenSSL uprobes, which are
  validated with HTTP (above) but not yet with a MySQL client.
- **HTTP/2 joined mid-connection** (agent started after the connection was
  opened): HPACK state is lost, so most headers, including the path, cannot be
  decoded until a new connection is opened.
- **Large capture gaps in HTTP/2** (several frames lost) reset that
  connection's parser. Gaps inside a single DATA frame are handled. Over TLS a
  gap only occurs past 16 KB per read/write call.
- **Per-packet capture is truncated at 4 KB** (16 KB per TLS read/write, in
  four events). Larger messages are reassembled where the protocol allows it. `panopticon_capture_truncated` counts what was
  cut.
- **TLS addresses are learned on the connection's first socket I/O inside a
  hooked call.** Until then, and on kernels where neither the sock tracepoints
  nor fentry/kprobes are available, TLS exchanges are exported without
  addresses and are left out of the service graph.
- **Statically linked TLS** other than Go (BoringSSL in Envoy, rustls, Java)
  is not covered, nor are Go binaries stripped of their symbol table.
- **Kafka is recognised by port 9092 only** (no magic bytes); brokers on other
  ports are not parsed. Compressed record batches (gzip, snappy, lz4, zstd)
  are framed and scored for topic and status, but their records are not
  decoded, so PII inside them is not visible. Each messaging protocol is
  scored against one server implementation (Kafka 3.8, RabbitMQ 3.13, a
  dnspython server).

## 8. Reproducing

Requirements: root on Linux 5.8+, a release build
(`cargo build -p panopticon-agent --release`), Docker for the database and
messaging runs, iproute2, Python with `pip install redis 'psycopg[binary]'
pymysql mysql-connector-python cryptography grpcio confluent-kafka kafka-python
pika dnspython`, and Go for the load generator and the Go TLS oracle.

```bash
# HTTP/1.1 accuracy, kernel cost, agent CPU/RSS. Fails below 99% recall.
sudo tests/oracle/run.sh 2000 1234
sudo tests/oracle/run.sh 5000 42          # load run

# HTTPS through the OpenSSL and Go TLS uprobes (client and server views).
# Needs openssl and go.
sudo env PATH="$PATH" tests/oracle/run_tls.sh 1000 42   # OpenSSL and Go stacks

# Redis, PostgreSQL, MySQL, gRPC. Fails if any protocol is below 99% recall.
sudo tests/oracle/run_protocols.sh 500 7

# Kafka, RabbitMQ (AMQP 0-9-1), DNS. Fails below 99% recall or on any leak.
sudo tests/oracle/run_messaging.sh 500 7

# Sustained load: concurrency, duration, rate (0 = max), newconn (1 = one
# request per connection). Reports recall, drops by cause, CPU and RSS.
sudo tests/load/run_load.sh 64 20s
sudo tests/load/run_load.sh 64 30s 0 1

# Fixed rate (scaling study): 4K connections at 20K req/s, reporting achieved
# vs target, client latency and server CPU; then the same load with no agent.
sudo tests/load/run_load.sh 4096 20s 20000
sudo NO_AGENT=1 tests/load/run_load.sh 4096 20s 20000

# The cgroup_skb backend: unscoped, scoped to the server (pid_filter), with
# every packet out of scope, and over loopback (node-local traffic).
# SCOPE also takes cgroup, head and sample; SERVER_LATE=1 creates the
# server's listener after the agent starts (add
# TOML='pid_filter_listener = "creator"' for the recall table above).
sudo BACKEND=cgroup_skb tests/load/run_load.sh 64 15s 5000
sudo BACKEND=cgroup_skb SCOPE=server tests/load/run_load.sh 64 15s 5000
sudo BACKEND=cgroup_skb SCOPE=other tests/load/run_load.sh 64 15s 5000
sudo BACKEND=cgroup_skb LOOPBACK=1 tests/load/run_load.sh 64 15s 5000

# User-space cost per event, one core: record a capture, then replay it
# (with your config; add --json-export /dev/null to include export).
sudo ./target/release/panopticon-agent -i eth0 --privacy-mode full --capture-raw /tmp/load.pncap
./target/release/panopticon-agent --replay-bench /tmp/load.pncap

# PII detection accuracy (no root, any OS); prints the per-type table.
# Regenerate the corpus only when changing the generator.
cargo test -p panopticon-agent pii_accuracy -- --nocapture
python3 tests/pii/gen_corpus.py

# Micro-benchmarks
cargo bench -p panopticon-agent --bench parser_throughput --bench pii_regex --bench protocol_detect --bench credential_rules

# Fuzzing (nightly)
cd fuzz && cargo +nightly fuzz run parsers -- -max_total_time=600
```

Each runner exits non-zero if recall is below the minimum or if any raw PII
value appears in the export. The same three runs execute in CI on pull
requests (`.github/workflows/oracle.yml`, also runnable by hand from the
Actions tab).

If Python is installed in a virtualenv, point the runners at it with
`PYTHON=/path/to/venv/bin/python`. Benchmarks build with a stub eBPF object,
so rebuild the release agent before running the oracles again.
